### 스냅샷(Snapshot) 패턴이란?

스냅샷 패턴은 특정 시점의 데이터 상태를 복사본으로 만들어 두고, 원본을 직접 순회하거나 수정하지 않고 복사본을 기준으로 안전하게 작업하는 방식입니다.

### 이 패턴을 사용하는 이유 (이터레이터 무효화 방지)

만약 스냅샷을 찍지 않고, 원본 그리드 데이터(`GridMap`)를 직접 보면서 블록을 폭파시킨다고 가정해 보겠습니다.

  1. `MapManager`(맵 매니저)이 원본 그리드 데이터를 폅니다. "1번 줄에 있는 A블록, 터져라!"

  2. A블록이 터지면서 **자신의 이름을 그리드 데이터에서 지워버립니다** (`RemoveBlockFromGrid`).

  3. `MapManager`이 "이제 다음 줄을 읽어야지..." 하고 그리드 데이터를 보는데, **1번 줄이 지워지면서 글씨가 위로 당겨지고 그리드 데이터 내용이 변경되어 순회 기준이 무효화됩니다.**

  4. 컴퓨터는 "어? 나 지금 어디 읽고 있었지?!" 하고 길을 잃어버리고, **잘못된 메모리 주소를 참조하면서 크래시가 발생할 수 있습니다.**

이렇게 리스트(그리드 데이터)를 순서대로 읽고 있는 도중에, 그 리스트의 내용물을 마음대로 지우거나 추가해서 반복문이 망가지는 현상을 컴퓨터 공학 용어로 '이터레이터 무효화(Iterator Invalidation)'라고 부릅니다.

### 🛡️ 코드가 작동하는 방식 (방어 완료)

원본 `GridMap`을 순회하면서 동시에 수정하지 않기 위해, 먼저 별도 배열에 값을 복사한 뒤 복사본을 기준으로 처리합니다.

C++

```plain text
// 1. 복사본 배열을 한 장 꺼냅니다.
TArray<ABlock*> BlocksToClear;

// 2. 📸 현재 그리드 데이터(GridMap)에 있는 모든 블록들을 복사본 배열에 저장합니다.
GridMap.GenerateValueArray(BlocksToClear);
```

이제 이후 `MapManager`는 복사본(`BlocksToClear` 배열)을 기준으로 순회합니다.
`MapManager`은 원본 그리드 데이터(`GridMap`)를 먼저 비우고(`GridMap.Empty()`), 복사본 배열을 보면서 각 블록에 파괴 명령(`ForcePop`)을 내립니다. 블록들이 터지면서 상태를 변경하더라도, `MapManager`이 보고 있는 복사본에는 아무런 영향을 주지 않으므로 게임이 절대 튕기지 않고 안정적으로 돌아가게 됩니다

# 그리드 데이터(GridMap)

### 1. 그리드 데이터가 없다면 무슨 일이 벌어질까? (물리 엔진의 한계)

만약 그리드 데이터가 없다면, 내 위에 어떤 블록이 있는지 확인하기 위해 매번 허공에 레이저(Raycast)를 쏘거나, 충돌체 박스(Overlap)를 그려서 검사해야 합니다.
블록이 1~2개면 괜찮지만, 화면에 블록이 100개가 넘어가면 매 프레임 큰 물리 연산 비용이 발생하여 폰이 뜨거워집니다. 게다가 소수점 오차 때문에 블록이 살짝 삐뚤어지면 레이저가 빗나가서 버그가 터지기도 하죠.

### 2. `MapManager`의 절대 그리드 데이터 (`TMap<FIntPoint, ABlock*> GridMap`)

그래서 맵 매니저는 물리 엔진에 의존하지 않고, 별도의 논리 좌표 데이터인 `GridMap`을 유지합니다. 이것이 바로 `GridMap`입니다.

- `FIntPoint`: 엑셀의 열과 행 (예: B열 3행 -> X:1, Y:2)

- `ABlock*`: 해당 좌표에 배치된 블록 포인터

좌표 기반 조회는 평균적으로 O(1)에 가까운 비용으로 처리할 수 있습니다.

### 3. 그리드 데이터 관리의 4단계 핵심 로직

### 📝 입사 (RegisterBlock)

새 블록이 스폰될 때 일어나는 일입니다.

- `MapManager`은 그리드 데이터의 `(Col, Row)` 칸에 새 블록의 연락처를 적습니다.

- 블록의 목에 걸린 좌표 값(`GridX`, `GridY`)에 자기 자리가 어딘지 기록합니다. 이제 블록은 자기가 엑셀표의 어디에 위치해 있는지 참조할 수 있습니다.

### 🔍 조회 (GetBlockAtGrid)

- "현재 블록의 오른쪽(`GridX + 1`)에 누가 있지?" 궁금할 때, 물리 엔진(레이캐스트)을 쓰지 않습니다.

- `MapManager`의 그리드 데이터에서 `(X+1, Y)` 칸을 열어보기만 하면 0.0001초 만에 그 자리에 있는 블록을 찾아냅니다. (이것이 같은 색깔 블록을 찾는 `FloodFill`의 핵심 원리입니다!)

### 🔥 퇴사 및 데이터 백지화 (RemoveBlockFromGrid)

블록이 파괴될 때(`Pop`), 시각적인 폭발(플립북)이 일어나기 전에 **데이터부터 먼저 지웁니다.**

- `MapManager`은 그리드 데이터에서 그 블록의 연락처를 제거합니다.

- 블록은 좌표 값을 반납(`GridX = -1, GridY = -1`)하여, 자신이 더 이상 그리드에 등록되지 않은 상태임을 명시합니다.

### 중력 제어 (`ProcessFalling`) - 핵심 로직

블록이 하나 터졌을 때 그 위에 있는 블록들을 밑으로 떨어뜨리는 로직입니다.

1. 방금 터진 빈자리 바로 윗칸부터 맨 꼭대기까지 그리드 데이터를 거꾸로 훑고 올라갑니다.

2. 블록을 발견하면, 그 블록의 발밑에 빈칸(`IsGridEmpty`)이 몇 개나 있는지 그리드 데이터만 보고 계산합니다.

3. 3칸이 비어있다면, **화면에서 블록이 떨어지기도 전에 ****`MapManager`****은 이미 그리드 데이터에서 블록의 자리를 3칸 아래로 지우고 새로 써버립니다. (데이터 선점)**

4. 그리드 데이터 정리가 끝나면, 블록에게 "목표 좌표로 낙하하라"(`PrepareToFall`)고 명령만 던집니다.

### 이 로직의 장점

화면 속에서 블록이 천천히 흔들리며 떨어지고(시각적 연출) 있더라도, **논리 데이터 속에서는 이미 모든 블록이 바닥에 도착해서 정리가 끝난 상태**입니다.
그래서 떨어지는 도중에 플레이어가 조작을 하거나 다른 블록이 터져도 상태를 안정적으로 통제할 수 있습니다.

그리드 데이터 구조를 사용하면 물리 오차에 의존하지 않고 블록 위치와 연결 관계를 안정적으로 관리할 수 있습니다. 이 구조는 동일 색상 블록을 탐색하는 플러드 필(Flood Fill) 알고리즘의 기반이 됩니다.

## 1. 블록 상태(EBlockState)에 따른 Tick 로직

이 코드는 게임 개발에서 널리 사용하는 **유한 상태 머신(FSM, Finite State Machine)** 패턴을 Unreal Engine의 `Tick` 제어와 결합한 구조입니다.

### 🔄 상태 전환과 `Tick` 제어 메커니즘

기존 유니티 스타일의 코드는 모든 블록이 항상 `Update()`를 켜두고 내부에 타이머나 상태를 매 프레임 검사합니다. 블록이 300개면 매 프레임 300번의 불필요한 루프가 돕니다.

리팩토링한 구조는 블록이 실제로 동작해야 할 때만 `Tick`을 활성화하는 방식입니다.

1. **`EBlockState::Idle`**** (대기 상태)**

  - 블록이 바둑판 안에서 가만히 멈춰 있는 대기 상태입니다.

  - 이때는 `SetActorTickEnabled(false)`를 통해 **`Tick`**** 함수 자체를 비활성화합니다.** CPU가 해당 블록의 Tick을 처리하지 않으므로 연산 비용이 0%가 됩니다.

2. **`EBlockState::Anticipating`**** (낙하 전 덜덜 흔들림)**

  - 발밑의 블록이 터져서 "낙하 준비 상태" 하고 인지한 순간입니다.

  - `PrepareToFall()`이 호출되면서 `SetActorTickEnabled(true)`로 **비활성화되어 있던 ****`Tick`****을 다시 활성화합니다.**

  - **수학적 연출:** 매 프레임 삼각함수인 `FMath::Sin(시간 * 주파수) * 진폭`을 계산하여 자식 컴포넌트인 스프라이트만 로컬 좌표로 위아래로 정밀하게 흔들어 줍니다. 루트(Root) 좌표는 고정되어 있어 데이터 오염이 없습니다.

3. **`EBlockState::Falling`**** (실제 낙하)**

  - 타이머가 끝나고 실제로 물리적 이동을 시작하는 상태입니다.

  - **보간(Interpolation) 연출:** `FMath::VInterpConstantTo` 함수를 사용하여 매 프레임 일정한 속도(`400.f`)로 `targetLocation`을 향해 부드럽게 미끄러지듯 내려갑니다.

  - **도착 스냅 및 다시 잠들기:** 목적지와의 거리가 `1.0f` 미만으로 좁혀지면, 소수점 오차를 방지하기 위해 목적지 좌표로 완전히 정렬한 뒤(`SetActorLocation(targetLocation)`), 상태를 다시 `Idle`로 바꾸고 **`SetActorTickEnabled(false)`****로 ****`Tick`****을 다시 비활성화합니다.**

## 2. ExecuteFloodFill() 재귀 함수와 구조적 분석

이 함수는 알고리즘적으로는 **DFS(Depth-First Search, 깊이 우선 탐색) 기반의 플러드 필(Flood Fill)** 알고리즘이며, 게임 아키텍처 관점에서는 **그리드 데이터 기반 논리 탐색 패턴**입니다. 쉽게 말해 그림판에서 '페인트통 툴'을 부었을 때 같은 색 영역이 전체적으로 퍼져나가는 원리입니다.

### 🛠️ 디자인 패턴이 아니라 알고리즘에 가까운 이유

이것은 특정 디자인 패턴(싱글톤, 옵저버 등)이라기보다는 **격자형 보드게임의 데이터 탐색 알고리즘**에 가깝습니다.
물리 엔진(Raycast나 이중 For문)을 사용해 주변 블록을 찾는 물리 기반 방식과 달리, `MapManager`의 그리드 데이터(`GridMap`)만을 0.0001초 만에 스캔하여 탐색 비용을 줄이는 방식입니다.

### 🏃 코드가 실행되는 5단계 탐색 흐름

함수가 실행되면 컴퓨터의 메모리 스택(Stack)에는 다음과 같은 순서로 파도치듯 연산이 쌓이고 풀립니다.

### 1단계: 철저한 방어선 (Base Case)

C++

```plain text
if (CurrentBlock == nullptr || CurrentBlock->blockColor != TargetColor ||
    CurrentBlock->currentState != EBlockState::Idle || OutMatchedBlocks.Contains(CurrentBlock)) return;
```

- 재귀 함수는 멈추는 조건(Base Case)이 없으면 무한 루프에 빠져 프로그램이 중단될 수 있습니다.

- 이 조건문은 **"빈 공간이거나 / 색깔이 다르거나 / 떨어지는 중이거나 / ⚠️이미 아까 찾은 명단에 있으면"** 즉시 함수를 끝내고 뒤로 돌아가라(`return`)고 명령합니다. 특히 `Contains` 검사는 이미 확인한 블록을 또 확인해서 무한 루프에 빠지는 것을 완벽히 방지합니다.

### 2단계: 신분 등록

C++

```plain text
OutMatchedBlocks.Add(CurrentBlock);
```

- 방어선을 통과했다는 것은 "현재 블록은 기준 색상과 일치하며 탐색 대상입니다"라는 뜻입니다.

- 참조자(`&`)로 연결된 원본 바구니(`TSet`)에 자기 자신을 추가합니다. `TSet` 자료구조 특성상 중복 데이터는 알아서 걸러집니다.

### 3단계: 그리드 데이터(Grid) 기반 방향 탐색

C++

```plain text
FIntPoint Dirs[4] = { FIntPoint(0, 1), FIntPoint(0, -1), FIntPoint(1, 0), FIntPoint(-1, 0) };
```

- 허공에 레이저를 쏘지 않고, 자신의 좌표 값에 적힌 `(gridX, gridY)` 칸을 기준으로 **하, 상, 우, 좌**의 가상 좌표를 수학적으로 계산합니다.

### 4단계 & 5단계: `MapManager` 그리드 데이터 조회와 자가 복제 (재귀 호출)

C++

```plain text
ABlock* NextBlock = mapManagerRef->GetBlockAtGrid(NextX, NextY);
ExecuteFloodFill(TargetColor, NextBlock, OutMatchedBlocks);
```

- `MapManager`(`MapManager`)에게 "인접 좌표에 블록이 있는지 확인합니다" 물어봅니다.

- 인접 블록이 존재하면, 그 블록을 대상으로 `ExecuteFloodFill`을 재귀 호출합니다.

이 과정에서 함수는 상하좌우 방향으로 탐색을 확장하며, 인접한 동일 색상 블록을 `TSet`에 수집합니다. 탐색이 벽이나 다른 색 블록에 부딪혀 막히면, 쌓였던 재귀 함수들이 역순으로 반환되며 최종적으로 터뜨려야 할 파괴 대상 블록 목록만 결과로 남습니다.

- **Flood Fill 로직:** 물리 연산 대신 그리드 인덱스 검색과 재귀 탐색을 결합하여, 다수의 연쇄 파괴를 안정적으로 처리하도록 구현했습니다.

### 1. 매 프레임 UI 업데이트의 비용

현재 `NativeTick` 안에서 산소, 깊이, 점수, 레벨을 **매 프레임 무조건 업데이트**하고 있습니다.

C++

```plain text
void UInGameHUDWidget::NativeTick(const FGeometry& MyGeometry, float InDeltaTime){
    if (statusSubsystemRef)
    {
       // 값이 바뀌지 않아도 매 프레임 실행되는 갱신 로직입니다.
       UpdateOxygenUI(statusSubsystemRef->currentOxygen);
       UpdateNumberUI(statusSubsystemRef->currentDepth, HB_Depth);
       UpdateNumberUI(statusSubsystemRef->currentScore, HB_Score);
       UpdateNumberUI(statusSubsystemRef->currentLevel, HB_Level);
    }
}
```

UI 업데이트(특히 `SetText`나 텍스처 변경)는 엔진에서 가장 무거운 연산 중 하나입니다. 점수나 깊이가 변경되지 않았는데도 매 프레임 UI를 갱신하면 모바일 또는 저사양 환경에서 프레임 드랍이 발생할 수 있습니다.

### 해결 방법: 값이 변경될 때만 업데이트하기 (Dirty Flag 패턴)

이전 프레임의 점수를 기억해 두고, 이번 프레임의 점수와 비교해서 **값이 달라졌을 때만 UI 갱신 함수를 호출**하는 기법을 써야 합니다.

먼저 헤더 파일(`InGameHUDWidget.h`)의 `InternalState` 구역에 과거 값을 기억할 변수를 추가해 줍니다.

C++

```plain text
// --- 5. 캐싱 및 내부 상태 데이터 ---
#pragma region InternalState
private:
    class UGameStatusSubsystem* statusSubsystemRef;
    class UMaterialInstanceDynamic* oxygenDynamicMaterial;

    // 🌟 [추가] 값의 변화를 감지하기 위한 캐싱 변수들
    float lastOxygen = -1.0f;
    int32 lastDepth = -1;
    int32 lastScore = -1;
    int32 lastLevel = -1;
#pragma endregion
```

이후 `.cpp`의 `NativeTick` 함수에서 값 변경 여부를 검사한 뒤 필요한 UI만 갱신하도록 수정합니다.

C++

```plain text
void UInGameHUDWidget::NativeTick(const FGeometry& MyGeometry, float InDeltaTime){
    Super::NativeTick(MyGeometry, InDeltaTime);

    if (statusSubsystemRef)
    {
       // 1. 산소가 바뀌었을 때만 갱신 (오차 범위 0.1 허용)
       if (!FMath::IsNearlyEqual(lastOxygen, statusSubsystemRef->currentOxygen, 0.1f))
       {
          UpdateOxygenUI(statusSubsystemRef->currentOxygen);
          lastOxygen = statusSubsystemRef->currentOxygen;
       }

       // 2. 깊이가 바뀌었을 때만 갱신
       if (lastDepth != statusSubsystemRef->currentDepth)
       {
          UpdateNumberUI(statusSubsystemRef->currentDepth, HB_Depth);
          lastDepth = statusSubsystemRef->currentDepth;
       }

       // 3. 점수가 바뀌었을 때만 갱신
       if (lastScore != statusSubsystemRef->currentScore)
       {
          UpdateNumberUI(statusSubsystemRef->currentScore, HB_Score);
          lastScore = statusSubsystemRef->currentScore;
       }

       // 4. 레벨이 바뀌었을 때만 갱신
       if (lastLevel != statusSubsystemRef->currentLevel)
       {
          UpdateNumberUI(statusSubsystemRef->currentLevel, HB_Level);
          lastLevel = statusSubsystemRef->currentLevel;
       }
    }
}
```

### 🎯 결론

- **Dirty Flag 패턴 적용:** 매 프레임 반복되던 텍스트 갱신을 값 변경 시점으로 제한하여 모바일 및 저사양 PC에서의 성능 부담을 줄였습니다.

- **입력 모드 버그 해결:** 게임 오버 창에서 재시작 버튼을 눌렀을 때, 캐릭터 조작이 입력되지 않는 버그를 사전에 예방했습니다.

# 🚀 미니드릴러(MiniDriller) 아키텍처 리팩토링 및 최적화 기록

## 1. 맵 매니저 (`AMapManager`) : 캡슐화와 안전성 확보

- **역할 분리 (Loose Coupling):** 맵 스폰 시 플레이어의 중력을 조작하고 입력을 막던 로직을 제거. 대신 플레이어 내부 함수(`OnMapTransitionStart`, `OnMapTransitionComplete`)를 호출하여 신호만 보내고, 캐릭터 스스로 상태를 제어하도록 캡슐화 보존.

- **스냅샷 패턴 (Snapshot Pattern) 적용:** 방사형 폭발(`ClearScreenBlocksRadially`) 연쇄 처리 중 `GridMap` 그리드 데이터가 삭제되며 발생하는 이터레이터 무효화(Iterator Invalidation) 크래시 방지. `GenerateValueArray()`를 통해 복사본을 만든 후 안전하게 폭발 처리.

- **인라인 최적화 (Inline):** `RemoveBlockFromGrid`와 같은 1줄짜리 가벼운 함수들은 헤더(`.h`)로 옮겨 함수 호출 오버헤드(Overhead)를 제거.

## 2. 부모 블록 (`ABlock`) : FSM 최적화 및 비즈니스 로직 분리

- **틱(Tick) 원천 봉쇄 최적화:** 200여 개의 풀링된 블록이 매 프레임 `Tick`을 돌며 CPU를 낭비하던 문제 해결. 생성자에서 `bStartWithTickEnabled = false`로 `Tick`을 비활성화하고, 오직 추락을 준비할 때(`Anticipating`)만 명시적으로 틱을 켜도록 수정.

- **전역 서브시스템 캐싱:** 매번 `GetSubsystem`을 호출하는 비용을 줄이기 위해 `BeginPlay`에서 한 번만 호출하여 `statusSubsystemRef`에 캐싱 적용.

- **비즈니스 로직 분리:** 블록 스스로 점수를 계산하고 효과음을 통제하던 로직을 완전히 제거. 서브시스템의 `ProcessBlockDestructionScore`로 점수 공식을 이관하여 블록은 '자신의 파괴'만 알리도록 설계 변경.

## 3. 자식 특수 블록 : 다형성(Polymorphism)과 생명주기 관리

- **산소 블록 (****`AOxygenBlock`****):** 충돌(Overlap)로 먹었을 때와 곡괭이로 캤을 때(Interact)의 중복 코드를 제거. Overlap 발생 시 내부적으로 `OnInteracted`를 재호출하도록 압축.

- **장애물 블록 (****`AObstacleBlock`****):** 오브젝트 풀링 시 체력(`currentHp`)과 파괴된 스프라이트가 원래대로 돌아오지 않던 버그 해결. `ResetBlockState()`를 오버라이드(Override)하여 풀링 반납 시 초기 상태로 되돌리는 자가 복구 로직 구현. (오프바이원 에러 방지)

- **배리어 블록 (****`ABarrierBlock`****):** 불필요한 입력 잠금 코드를 제거하고, 파괴 시 서브시스템에 직접 `LevelUp()`을 호출하여 직관적인 레벨업 사이클 완성.

## 4. 전역 서브시스템 (`UGameStatusSubsystem`) : 단일 통로(Centralized Path) 구축

- **죽음 처리 단일화:** 산소가 고갈되었을 때와 블록에 깔렸을 때 각각 다르게 처리되던 사망 로직 통합. 서브시스템이 직접 죽음을 판정하지 않고, `Driller->HandleDeath()`를 호출하여 **캐릭터가 죽음 애니메이션을 재생한 뒤 서브시스템 타이머를 멈추도록 단일 흐름으로 처리.**

- **중복 변수 제거:** 의미가 겹치던 `bIsDead`와 `bIsPlayerDead`를 `bIsPlayerDead` 하나로 통합하여 블루프린트와의 통신 및 상태 관리 일원화.

- **콤보 사운드 피치 조정:** 블록이 몇 개 터졌는지(BlockCount)를 매개변수로 받아, 콤보 수에 따라 사운드의 피치(Pitch)를 점진적으로 올려 타격감을 극대화하는 함수 구현.

## 5. UI 시스템 (`UInGameHUDWidget`) : 렌더링 최적화 및 뷰(View) 관리

- **더티 플래그(Dirty Flag) 패턴 적용:** 매 프레임(Tick)마다 점수, 깊이, 산소 UI를 강제로 덮어씌워 프레임 드랍을 유발하던 로직 개선. 과거의 값(`lastScore`, `lastOxygen` 등)을 캐싱해두고, **실제 데이터에 변화가 생겼을 때만 UI 업데이트 함수를 호출**하도록 성능 최적화를 적용했습니다.

- **입력 모드 초기화 버그 픽스:** 게임 오버 후 재시작(Restart) 버튼이나 타이틀(Title) 버튼을 눌렀을 때, `FInputModeUIOnly` 상태로 넘어가 플레이어 조작이 먹통이 되던 현상 해결. 맵 전환 직전에 `FInputModeGameOnly`로 복구 코드 추가.
